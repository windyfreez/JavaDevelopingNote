## 4. MySQL高频面试陷阱速记（生产必避坑）
1. 生产环境**绝对禁止物理外键**，物理外键会加剧锁竞争、引发死锁、降低写入性能、分库分表迁移极度困难，企业全部通过业务代码实现逻辑关联校验。
2. Spring 声明式事务**默认仅回滚运行时异常**，编译异常、检查异常不会触发回滚，必须手动配置 `rollbackFor` 统一回滚规则。
3. MySQL 默认 `RR` 可重复读隔离级别，**`MVCC` 解决快照读幻读，临键锁解决当前读幻读**，是两套机制共同解决幻读问题，并非单纯靠隔离级别。
4. `InnoDB` 行锁是**索引锁而非数据锁**，查询条件无索引、索引失效、字段类型不匹配，都会导致行锁升级为全表表锁，直接阻塞整表读写，是线上高频卡顿事故根源。
5. 索引列使用函数运算、左侧模糊匹配、隐式类型转换，**百分百触发索引失效**，走全表扫描。
6. 联合索引最左前缀法则由 `B+Tree` 排序结构决定，跳过前置字段直接导致索引部分失效或完全失效。
7. 间隙锁、临键锁**仅在 `RR` 可重复读隔离级别下生效**，`RC` 读已提交级别没有间隙锁，无法杜绝插入幻读。
8. 线上长事务危害极大，会长时间占用行锁、堆积大量 `undo_log`、阻塞 `DDL` 语句、加剧主从延迟、拖垮整体数据库性能。
9. 日常禁止使用 `select *`，会无法使用覆盖索引、强制回表查询、加载大量无用字段、浪费 IO 资源和内存。
10. `count(普通字段)` 会自动忽略 `null` 值，统计结果不准，`count(*)` 统计所有数据行，业务行数统计必须使用 `count(*)`。
11. 左外连接查询筛选条件如果写在 `where` 后面，会过滤掉 `null` 数据，直接降级为内连接，条件必须写在 `on` 关联后。
12. 动态 SQL 中单纯使用 `where 1=1` 拼接条件，会导致数据库优化器无法优化 SQL，索引失效，生产禁止使用。
13. MyBatis 模糊查询写 `LIKE '%#{name}%'` 会直接报错，必须用 `CONCAT('%',#{name},'%')`，`#{}` 不能放进引号内拼接。
14. `PageHelper.startPage()` 必须紧跟查询成对出现，中间异常未执行查询会导致 `ThreadLocal` 分页参数残留，线程复用时下一个不相关请求莫名被分页。
15. 间隙锁之间互不冲突但都禁止 INSERT，两个事务同持一段间隙锁后互相插入极易死锁；删除、更新不存在的记录同样会加间隙锁。
16. InnoDB 行锁在事务 `COMMIT`/`ROLLBACK` 时才统一释放（两阶段锁协议），UPDATE 语句执行完不提交，锁依然被持有，其他事务持续阻塞。
17. `DROP`/`TRUNCATE` 属于 DDL，ROW 格式 binlog 只记录删表动作不记录数据，闪回恢复无效，只能靠全量备份 + binlog 重放。
18. 索引失效不全是语法问题：命中行数超过全表约 20%~30% 时，优化器评估回表成本高于全表扫描，会主动放弃索引。

# 一、多表关系设计（数据库设计核心）
实际业务系统中，所有数据都是关联存在的，不可能单表独立存储。MySQL 通过外键机制定义表与表之间的关联关系，规范数据存储、减少数据冗余、保证数据完整性。标准关系分为一对多、多对多、一对一三种，其中一对多使用最多，多对多需要中间表，一对一用于冷热数据拆分。

## 1. 一对多关系
### 1.1 核心原理与业务场景
一对多是业务系统中最普遍的表关系，核心逻辑是：一张主表的单条数据，可以关联多张从表数据，但是从表的单条数据，只能归属一个主表数据。为了保证结构合理、无数据冗余，**外键字段必须建立在多的一方（从表）**。

如果将外键建立在一方主表中，主表需要存储海量从表 `id`，会导致字段无限扩张、数据极度冗余、无法维护。而从表存储主表 `id`，每条子数据仅保留一个父级标识，结构规整、查询高效、完全符合数据库设计三大范式。典型业务场景包含部门与员工、商品分类与商品、订单与订单明细、文章分类与文章。

### 1.2 实操语法规范
企业统一外键命名规范：`fk_从表名_主表名_关联字段名`，可读性强、便于维护。支持建表时直接定义外键、建表后动态追加外键两种方式。

```sql
-- 建表：部门主表
CREATE TABLE `dept` (
  `id` INT PRIMARY KEY AUTO_INCREMENT,
  `dept_name` VARCHAR(32) NOT NULL COMMENT '部门名称'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 建表时直接定义外键，员工从表（多方）
CREATE TABLE `emp` (
    `id` INT PRIMARY KEY AUTO_INCREMENT,
    `name` VARCHAR(20),
    `salary` DECIMAL(10,2),
    `dept_id` INT,
    CONSTRAINT `fk_emp_dept_dept_id` FOREIGN KEY(`dept_id`) REFERENCES `dept`(`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 已有数据表追加外键约束
ALTER TABLE `emp` 
ADD CONSTRAINT `fk_emp_dept_dept_id` 
FOREIGN KEY(`dept_id`) REFERENCES `dept`(`id`);
```

### 1.3 面试八股（高频口述）
**面试官提问：一对多关系为什么外键必须放在多的一方？放在一方会有什么问题？**

**口述回答**：一对多的核心设计原则就是外键归多方。如果外键放在一方主表中，主表需要存储所有从表的关联 `id`，会造成字段无限变长、数据严重冗余，完全无法维护。而将外键放在从表，每条子数据只存储一个父级 `id`，结构简洁、冗余最低、查询高效，完全符合数据库范式设计，是行业统一标准。

## 2. 多对多关系
### 2.1 核心原理与业务场景
多对多是双向一对多的特殊关系，两张业务表的数据可以互相关联多条对方数据，无法通过单外键直接建立关联。因此必须引入一张**中间关联表**解耦两张主表，中间表不存储任何业务数据，只存储两张主表的主键关联关系，实现双向多关联。

这种设计的最大优势是解耦、扩展性极强，新增关联关系、删除关联关系都只操作中间表，不会改动核心业务表数据。经典业务场景：学生与课程、用户与角色、订单与商品、文章与标签。

```sql
-- 用户表
CREATE TABLE `sys_user` (
  `id` INT PRIMARY KEY AUTO_INCREMENT,
  `username` VARCHAR(32) NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 角色表
CREATE TABLE `sys_role` (
  `id` INT PRIMARY KEY AUTO_INCREMENT,
  `role_name` VARCHAR(32) NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 用户角色中间表，实现多对多
CREATE TABLE `sys_user_role` (
  `user_id` INT NOT NULL,
  `role_id` INT NOT NULL,
  PRIMARY KEY (`user_id`,`role_id`),
  CONSTRAINT `fk_ur_user_id` FOREIGN KEY (`user_id`) REFERENCES `sys_user`(`id`),
  CONSTRAINT `fk_ur_role_id` FOREIGN KEY (`role_id`) REFERENCES `sys_role`(`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 2.2 面试八股（高频口述）
**面试官提问：多对多为什么必须使用中间表？能不能直接两张表关联？**

**口述回答**：不能直接两张表关联。多对多是双向关联，两边数据都能对应多条对方数据，单一外键无法实现双向绑定。引入中间表可以彻底解耦两张核心业务表，只维护关联关系，保证职责单一、结构清晰、扩展性强，避免数据冗余和结构混乱，是数据库设计的标准规范。

## 3. 一对一关系
### 3.1 核心原理与业务场景
一对一属于特殊的一对多，本质是在一对多基础上，给从表外键添加 `unique` 唯一约束，保证双方数据一一对应。一对一不用于普通关联，核心作用是**单表拆分、冷热数据分离**。

当一张表字段过多、包含大文本、长备注、图片地址等低频大字段时，整表查询会造成大量磁盘 IO 浪费，严重影响查询性能。通过一对一拆分，将高频查询的基础字段放在主表，低频、大字段放在副表，实现按需查询、冷热分离，大幅提升数据库吞吐量。典型场景：用户基础信息与身份证详情、商品基础信息与商品详情大文本。

```sql
-- 用户基础主表（高频访问）
CREATE TABLE `user_base` (
  `id` INT PRIMARY KEY AUTO_INCREMENT,
  `username` VARCHAR(32),
  `phone` VARCHAR(11)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 用户详情副表（大字段、低频访问）一对一
CREATE TABLE `user_detail` (
  `id` INT PRIMARY KEY AUTO_INCREMENT,
  `user_id` INT UNIQUE NOT NULL COMMENT '唯一约束，实现一对一',
  `id_card` VARCHAR(18),
  `avatar_url` VARCHAR(255),
  `self_intro` TEXT COMMENT '大文本自我介绍',
  CONSTRAINT `fk_ud_user_id` FOREIGN KEY (`user_id`) REFERENCES `user_base`(`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 3.2 面试八股（高频口述）
**面试官提问：一对一表拆分的意义是什么？为什么不全部放在一张表里？**

**口述回答**：主要是为了冷热数据分离和性能优化。单表字段过多、包含大字段时，普通查询会加载大量无用数据，造成磁盘 IO 浪费、查询变慢。拆分后高频字段独立查询，低频大字段按需关联查询，极大减少 IO 开销，提升整体接口响应速度和数据库并发性能。

## 4. 数据库设计三范式（1NF / 2NF / 3NF）
> 🎯【面试题】数据库三范式是什么？实际开发必须严格遵守吗？
> 参考答案：
> - **第一范式（1NF）**：字段不可再分，每个字段保持原子性。例如"地址"字段存"省市区"拼接字符串就违反1NF，应拆分为省、市、区多个字段；
> - **第二范式（2NF）**：在1NF基础上，非主键字段必须**完全依赖主键**，不能只依赖主键的一部分（针对联合主键）。例如订单明细表用`(order_id, product_id)`做联合主键，如果"订单日期"只依赖order_id，就违反2NF，需要拆分表；
> - **第三范式（3NF）**：在2NF基础上，非主键字段之间不能存在**传递依赖**。例如员工表存了`dept_id`又存`dept_name`，dept_name通过dept_id传递依赖主键，应拆出部门表，员工表只保留dept_id。
> 实际开发：3NF是理论基准，但为了查询性能会**反范式化**，刻意冗余一些字段（如订单快照中冗余商品名称、价格），用空间换时间，减少join；关键是冗余字段的一致性维护要有保障。

# 二、多表查询（业务开发核心）
实际业务开发中，80% 的查询都需要关联多张表获取整合数据。多表查询主要分为内连接和外连接两大类，核心区别是数据保留规则不同，开发必须根据业务场景选择对应连接方式，否则会出现数据缺失、数据错误等问题。

## 1. 内连接 `INNER JOIN`
内连接的核心逻辑是**只保留两张表的交集数据**，只有两张表中能够互相匹配的关联数据才会被查询出来，任意一方不存在匹配数据，都会直接过滤舍弃。内连接分为隐式连接和显式连接，企业开发统一推荐显式 `JOIN` 写法，结构清晰、便于维护、不易出错。

```sql
-- 显式内连接（企业开发推荐）
SELECT e.`id`,e.`name`,e.`salary`,d.`dept_name`
FROM `emp` e
INNER JOIN `dept` d ON e.`dept_id` = d.`id`
WHERE e.`salary` > 8000;

-- 隐式内连接，不推荐
SELECT e.`id`,e.`name`,d.`dept_name`
FROM `emp` e,`dept` d
WHERE e.`dept_id` = d.`id` AND e.`salary` > 8000;
```

## 2. 外连接
外连接会保留某一张表的全部数据，根据匹配情况填充另一张表数据，分为左外连接和右外连接，开发中**左连接使用占比 99%**，几乎不使用右连接。

左外连接以左表为基准，左表所有数据全部保留，右表匹配到数据则展示，匹配不到则填充 `NULL`；右外连接以右表为基准，逻辑相反，可读性差、极少使用。

```sql
-- 左外连接：查询所有员工，包含没有分配部门的员工
SELECT e.`id`,e.`name`,d.`dept_name`
FROM `emp` e
LEFT OUTER JOIN `dept` d ON e.`dept_id` = d.`id`;

-- 错误示范：条件写where，左连接降级为内连接
SELECT e.`id`,e.`name`,d.`dept_name`
FROM `emp` e
LEFT JOIN `dept` d ON e.`dept_id` = d.`id`
WHERE d.`dept_name` = '技术部';

-- 正确示范：筛选条件放在on后
SELECT e.`id`,e.`name`,d.`dept_name`
FROM `emp` e
LEFT JOIN `dept` d ON e.`dept_id` = d.`id` AND d.`dept_name` = '技术部';
```

### 2.1 面试八股（超高频）
**面试官提问：左连接 `on` 条件和 `where` 条件有什么本质区别？写错会有什么后果？**

**口述回答**：`on` 是表关联条件，用于匹配两张表的关联关系，不会过滤左表数据；`where` 是查询结果过滤条件，会对关联后的整体结果做筛选。如果把左连接的筛选条件写在 `where` 后面，会过滤掉右表为 `NULL` 的数据，直接导致左连接降级为内连接，出现业务数据缺失，是开发高频易错点。

# 三、MyBatis 动态 SQL
动态 SQL 是 MyBatis 最核心、最实用的功能之一，彻底解决了传统硬编码 SQL 的冗余问题。业务查询、更新条件往往是动态可变的，不同前端参数对应不同 SQL 语句，如果手动拼接会出现大量重复代码、语法报错、多余 `and`/`or`、多余逗号等问题，动态标签可以自动智能拼接、规避语法错误。

## 1. 核心标签底层原理与作用
- **`if` 标签**：最基础的单条件判断，判断参数是否非空，满足条件才拼接对应 SQL 片段，适用于动态查询、动态更新场景。
- **`where` 标签**：智能处理查询条件前缀，自动去除首个多余的 `and`、`or`，同时所有 `if` 条件不成立时，不会生成 `where` 关键字，彻底杜绝语法报错。
- **`set` 标签**：专门用于动态更新语句，自动去除最后一个字段更新后的多余逗号，避免动态字段拼接导致的 SQL 语法错误。
- **`foreach` 标签**：用于遍历集合、数组，实现批量插入、批量删除、`in` 范围查询，是批量操作核心标签。
- **`choose` 标签**：多条件互斥分支，类似 Java `switch` 语句，多个条件中只会匹配第一个满足的条件，适用于互斥查询场景。

```xml
<!-- where + if 动态查询示例 -->
<select id="queryEmp" resultType="com.xxx.entity.Emp">
    SELECT `id`,`name`,`salary`,`dept_id` FROM `emp`
    <where>
        <if test="name != null and name != ''">
            AND `name` LIKE CONCAT('%',#{name},'%')
        </if>
        <if test="minSalary != null">
            AND `salary` >= #{minSalary}
        </if>
    </where>
</select>

<!-- set + if 动态更新示例 -->
<update id="updateEmpSelective">
    UPDATE `emp`
    <set>
        <if test="name != null">`name` = #{name},</if>
        <if test="salary != null">`salary` = #{salary},</if>
        <if test="deptId != null">`dept_id` = #{deptId}</if>
    </set>
    WHERE `id` = #{id}
</update>

<!-- foreach in查询示例 -->
<select id="queryEmpByIds" resultType="com.xxx.entity.Emp">
    SELECT * FROM `emp`
    WHERE `id` IN
    <foreach collection="idList" item="item" open="(" separator="," close=")">
        #{item}
    </foreach>
</select>
```

### 面试八股（高频）
**面试官提问：开发中为什么禁止使用 `where 1=1` 拼接动态条件？**

**口述回答**：`where 1=1` 是老式不规范写法，虽然能拼接多条件，但会导致 MySQL 优化器无法正常优化 SQL，直接失效索引优化策略，同时代码可读性差、不规范。生产环境统一使用 `where` 动态标签替代，既能实现动态多条件拼接，又能保证 SQL 可优化、语法安全。

## 2. 动态 SQL 高频坑点：`foreach` 的坑与批量操作规范（面试高频）

### 面试八股（高频）
**面试官提问：`foreach` 标签有什么坑？生产环境如何安全使用？**

**口述回答**：`foreach` 的坑集中四处：
1. **SQL 超长坑**：`foreach` 是把集合内容拼接成**一条超长 SQL**，集合过大时超过 `max_allowed_packet`（默认约 4MB~64MB）直接报 `Packet too large`；超长 SQL 的解析、网络传输、优化成本也急剧上升。生产必须**分批拼接**，每批建议 500~1000 条；
2. **空集合坑**：集合为空时拼接出 `WHERE id IN ()`，是非法 SQL 直接语法报错，使用前必须判空；
3. **主键回填坑**：`foreach` 批量 `insert` 配合 `useGeneratedKeys="true"` 时，MyBatis/常见驱动默认**只能回填第一条记录的自增主键**，无法逐行回填，业务需要逐行主键时应改单条插入或插入后统一查询；
4. **参数名坑**：不指定 `collection` 时，`List` 默认取 `list`、数组默认取 `array`；多参数场景未用 `@Param` 显式命名会报 `There is no getter for property named 'xxx'`，必须显式 `@Param("ids")`；
5. **性能对比坑**：`for` 循环逐条 insert 是 **N 次网络往返 + N 次事务提交**，`foreach` 批量拼接**一次往返、一次提交**，批量写入必须用 `foreach` 并配合分批控制。

生产规范写法（分批 + 判空 + 显式 @Param）：

```xml
<!-- 每批 500 条，一条 SQL 提交 -->
<insert id="batchInsert" parameterType="list">
    INSERT INTO `emp`(`name`,`salary`,`dept_id`) VALUES
    <foreach collection="list" item="item" separator=",">
        (#{item.name},#{item.salary},#{item.deptId})
    </foreach>
</insert>
```

一句话：**`foreach` 的坑集中在"超长 SQL、空集合、主键回填、参数命名"四处，生产必须分批、判空、显式 `@Param`**。

## 3. `#{}` 与 `${}` 的区别（面试高频）

> 🎯【面试题】MyBatis 中 `#{}` 和 `${}` 的底层区别是什么？为什么 `${}` 有 SQL 注入风险？哪些场景必须用 `${}`？
> 参考答案：
> - **底层机制不同**：`#{}` 是**预编译占位符**，会被替换成 JDBC 的 `?`，通过 `PreparedStatement.setXXX()` 赋值，参数只作为"值"参与执行；`${}` 是**字符串拼接替换**，直接把参数字面量拼进 SQL，底层走 `Statement`；
> - **安全性不同**：`#{}` 天然防 SQL 注入，传入 `' or 1=1 --` 也只会被当成普通字符串值处理；`${}` 直接拼接，`where password = '${pwd}'` 传入 `' or '1'='1` 会变成 `where password = '' or '1'='1'`，直接绕过登录校验；
> - **类型处理不同**：`#{}` 自动处理类型，字符串自动加引号、日期自动格式化；`${}` 拼接字符串必须手动写引号，否则 SQL 语法报错；
> - **性能不同**：`#{}` 的 SQL 结构固定，数据库可缓存执行计划，重复执行只需传 `?` 的值；`${}` 每次拼出的 SQL 都可能不同，无法复用执行计划，需要重新解析优化。
>
> **为什么还要保留 `${}`**：JDBC 预编译的 `?` 只能代表**值**，不能代表表名、字段名、排序关键字等**元数据**。动态表名 `select * from ${tableName}`、动态排序 `order by ${column}`（用 `#{}` 会变成 `order by 'name'`，属于非法排序）只能用 `${}`；`${}` 接收外部参数时必须做白名单校验，禁止前端值直接透传。

> ⚠️注意：模糊查询不能写 `LIKE '%#{name}%'`，`#{}` 整体会被当成一个字符串参数导致引号错乱报错，必须写 `LIKE CONCAT('%',#{name},'%')`。
> 一句话：**能用 `#{}` 绝不用 `${}`：`#{}` 走 PreparedStatement 预编译防注入、可复用执行计划；`${}` 是字符串替换有注入风险，仅限动态表名、列名、排序字段等元数据场景**。

## 4. PageHelper 分页插件原理（面试高频）

> 🎯【面试题】PageHelper 分页插件的底层原理是什么？为什么 `startPage` 必须紧跟查询？有什么坑？
> 参考答案：PageHelper 本质是一个 **MyBatis 拦截器（Interceptor）**，利用**动态代理 + SQL 改写**，在不侵入业务代码的情况下透明实现分页，核心流程四步：
> 1. **参数传递**：调用 `PageHelper.startPage(1, 10)` 时，把分页参数存入 **`ThreadLocal`**，让参数跨 Service/DAO 层传递到底层拦截器；
> 2. **拦截请求**：PageHelper 实现了 `Interceptor` 接口，拦截 **`Executor` 的 query 方法**，执行查询前先检查 `ThreadLocal` 中有没有分页参数；
> 3. **SQL 改写**：有分页参数就执行两项操作——用 `JSqlParser` 解析原 SQL，改写成 `SELECT COUNT(0) FROM (原SQL)` 先查总记录数；再按数据库方言（Dialect，通过 `DatabaseMetaData` 自动识别 MySQL/Oracle 等）给原 SQL 拼上 `LIMIT ?, ?`；
> 4. **清理环境**：查询结束后在 `finally` 中 `ThreadLocal.remove()` 清理分页参数，防止残留污染。

> ⚠️注意：`startPage` 与查询必须**紧跟成对出现**。`ThreadLocal` 绑定线程，如果中间插入了复杂逻辑或异常导致没有真正执行查询，分页参数会**残留在线程池的线程里**，线程被复用时下一个毫不相关的请求会莫名被分页，必要时手动调用 `PageHelper.clearPage()`。另外关联查询带 `collection` 嵌套映射时，PageHelper 的总数统计可能不准。
> 分页返回的是 `Page<E>` 对象（继承 `ArrayList`），可直接当 `List` 用，也可包装成 `PageInfo` 拿总条数、总页数。
> 一句话：**PageHelper = 拦截器拦截 Executor + ThreadLocal 传参 + JSqlParser 改写 SQL，一次请求生成 count 和 limit 两条 SQL；startPage 与查询必须成对出现，防 ThreadLocal 残留**。

# 四、事务、ACID、隔离级别、MVCC（面试重中之重）
事务是数据库保证数据安全、并发安全的核心机制，所有转账、下单、扣库存、支付等核心业务，全部依赖事务保证数据一致性。面试重点考察底层原理而非使用，`ACID` 特性、并发问题、隔离级别、`MVCC` 无锁并发是必问核心。

```sql
-- 手动事务演示
START TRANSACTION; -- 开启事务
UPDATE `account` SET `balance`=`balance`-100 WHERE `id`=1;
UPDATE `account` SET `balance`=`balance`+100 WHERE `id`=2;
COMMIT; -- 提交事务

-- 出错时回滚
-- ROLLBACK;

-- 查看当前会话隔离级别
SELECT @@tx_isolation;
-- 设置会话隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

## 1. 事务 ACID 四大特性（底层保障机制）
`ACID` 是事务的四大核心特性，每一个特性都对应 MySQL 一套底层机制支撑，并非空概念：

- **原子性（Atomicity）**：事务是最小执行单元，不可拆分，所有操作要么全部成功提交，要么全部失败回滚。由 `undo_log` 回滚日志保证。
- **一致性（Consistency）**：事务执行前后，数据库约束、业务数据状态始终合法一致，不会出现非法中间数据，是事务的最终目标。
- **隔离性（Isolation）**：多事务并发执行时，互相隔离、互不干扰，保证并发数据安全。由锁机制 + `MVCC` 多版本并发控制共同保证。
- **持久性（Durability）**：事务一旦提交成功，数据修改永久落地，服务器宕机、断电不会丢失数据。由 `redo_log` 重做日志保证。

## 2. 并发事务三大问题
多事务并发执行时，隔离不足会出现三类数据问题，严重影响业务正确性：

|问题类型|详细现象与危害|
|---|---|
|脏读|一个事务读取到了其他事务**未提交**的临时数据，如果对方事务回滚，当前读取的数据就是无效脏数据，严重影响业务判断。|
|不可重复读|同一个事务内，两次查询同一条数据，结果不一致。因为中间被其他事务修改并提交，导致单次事务内数据不稳定。|
|幻读|同一个事务按条件查询无数据，执行插入时报错数据已存在，或前后查询数据行数不一致，像出现幻影数据，多出现于批量操作场景。|

## 3. 四大事务隔离级别
MySQL 提供四级隔离级别，级别越高数据安全性越高、并发性能越低，逐级规避并发问题：

1. **读未提交**：最低级别，存在脏读、不可重复读、幻读，生产完全不用。
2. **读已提交(`RC`)**：只能读取已提交数据，解决脏读，存在不可重复读、幻读。
3. **可重复读(`RR`、MySQL默认)**：解决脏读、不可重复读，存在理论幻读，底层通过 `MVCC`+临键锁彻底解决业务幻读。
4. **串行化**：最高级别，事务串行执行，解决所有问题，性能极低，极少使用。


## 4. MVCC 多版本并发控制（核心重难点）
`MVCC` 是 `InnoDB` 实现高并发事务的核心机制，全称多版本并发控制，核心作用是**无锁实现读写并发**，极大提升数据库并发性能，是 MySQL 高性能的根本原因之一。

`MVCC` 底层依靠 `undo_log` 版本链 + `readView` 一致性视图实现。数据被修改时，旧数据会存入 `undo_log` 形成历史版本链，普通查询不会加锁，而是根据当前事务的 `readView` 读取符合规则的历史快照版本，实现读写不冲突。

`MVCC` 区分两种读取方式：**快照读**和**当前读**。普通 `select` 查询属于快照读，走 `MVCC` 无锁查询；`update`、`delete`、`insert`、`select ... for update`、`select ... lock in share mode` 属于当前读，走锁机制，读取最新数据。

```sql
-- 快照读（普通select，不加锁）
SELECT * FROM `emp` WHERE `id` = 1;

-- 当前读，加排他锁
SELECT * FROM `emp` WHERE `id` = 1 FOR UPDATE;

-- 当前读，加共享锁
SELECT * FROM `emp` WHERE `id` = 1 LOCK IN SHARE MODE;
```

### 面试八股（必背）
**面试官提问：MySQL 默认 `RR` 隔离级别，真的彻底解决幻读了吗？原理是什么？**

**口述回答**：彻底解决了业务层面的幻读问题，是两套机制共同实现的。对于普通快照读，依靠 `MVCC` 多版本机制，读取历史数据快照，看不到其他事务新增数据，避免幻读；对于加锁的当前读，依靠临键锁锁定索引区间，禁止其他事务插入数据，杜绝幻读。两者结合，彻底解决 `RR` 级别幻读问题。

## 5. 第四类并发问题：丢失更新（Lost Update）

> 🎯【面试题】除了脏读、不可重复读、幻读，并发事务还有什么问题？什么是丢失更新？怎么解决？
> 参考答案：并发问题分两类：**读一致性问题**（脏读、不可重复读、幻读）和**更新丢失问题**：
> - **第一类丢失更新（回滚覆盖）**：事务 A 回滚时，把事务 B 已提交的更新一并覆盖回退，现代数据库底层已通过锁机制杜绝，面试一般不深问；
> - **第二类丢失更新（提交覆盖，重点）**：A、B 同时读到余额 100，A 扣 50 写回 50，B 扣 30 写回 70，A 先提交、B 后提交，最终余额 70，**A 的更新被 B 覆盖丢失**。这类读-写-写交错问题靠隔离级别并不能完全杜绝；
> - **解决方案（应用层实现）**：**乐观锁**——表加 `version` 字段，`UPDATE ... SET money=?, version=version+1 WHERE id=? AND version=旧值`，影响行数为 0 说明被别人改过，重试整个流程；**悲观锁**——`SELECT ... FOR UPDATE` 先加排他锁锁住行再修改，适合写冲突激烈的场景。

> ⚠️注意：不可重复读与幻读的经典区分——不可重复读针对**同一行数据的值被修改**（`UPDATE`/`DELETE`），行锁即可解决；幻读针对**结果集行数变化**（`INSERT`），必须靠间隙锁或 MVCC 解决。

## 6. MVCC 深度原理：隐藏字段、ReadView 可见性算法与 RC/RR 差异（必背）

> 🎯【面试题】MVCC 的实现细节：隐藏字段有哪些？ReadView 里有什么？可见性怎么判断？
> 参考答案：MVCC = **隐藏字段 + undo log 版本链 + ReadView 可见性判断**，三大支柱：
> - **隐藏字段**：InnoDB 每行数据自动携带 `DB_TRX_ID`（最后修改该行的事务 ID）、`DB_ROLL_PTR`（回滚指针，指向该行上一个版本在 undo log 中的位置），无主键时还有隐藏主键 `DB_ROW_ID`；
> - **版本链**：事务修改数据前先把旧值拷入 undo log，再更新当前行的 `DB_TRX_ID` 并让 `DB_ROLL_PTR` 指向旧版本，多次修改形成版本链——最新值在表里，历史值在 undo log 里；
> - **ReadView 四个核心字段**：`m_ids`（生成视图时所有**活跃未提交**的事务 ID 列表）、`min_trx_id`（活跃列表最小值）、`max_trx_id`（系统将分配给下一个事务的 ID）、`creator_trx_id`（创建该视图的当前事务 ID）。

**可见性判断规则**（拿当前行的 `DB_TRX_ID` 与 ReadView 比对）：
1. 等于 `creator_trx_id`：自己修改的，**可见**；
2. 小于 `min_trx_id`：修改该行的事务在视图创建前已提交，**可见**；
3. 大于等于 `max_trx_id`：视图创建之后才开启的事务，**不可见**；
4. 介于两者之间：在 `m_ids` 中（还未提交）**不可见**；不在（已提交）**可见**。

不可见就顺着 `DB_ROLL_PTR` 沿版本链回溯上一个版本，重复判断，直到找到可见版本为止。

> 🎯【面试题】`RC` 和 `RR` 都基于 MVCC，为什么一个存在不可重复读、一个能解决？
> 参考答案：本质差异是 **ReadView 的生成时机**：`RC`（读已提交）**每次执行 SELECT 前都重新生成**一个 ReadView，别人刚提交的数据立刻可见，所以两次读结果可能不同；`RR`（可重复读）只在**事务第一条 SELECT 时生成一个**，整个事务全程复用，快照始终一致，实现可重复读。
> 一句话：**MVCC 靠"版本链 + ReadView 过滤"实现读不加锁；RC 每句一换 ReadView、RR 全程一个 ReadView，一个生成时机解释两大隔离级别的核心差异**。

# 五、三大日志机制（底层核心）
MySQL 所有事务安全、崩溃恢复、主从复制、数据持久化，全部依赖三大日志机制，是底层原理面试必考重点，三者各司其职、互不冲突。

## 1. redo log 重做日志
`redo log` 是 `InnoDB` 引擎级别的日志，核心作用是**保证事务持久性、实现崩溃恢复**。MySQL 为了提升性能，不会实时把内存数据刷入磁盘，而是先写入 `redo log` 日志，事务提交即视为持久化。如果服务器宕机，重启后会根据 `redo log` 重做未落地的数据，保证数据不丢失。

## 2. undo log 回滚日志
`undo log` 同样是 `InnoDB` 引擎日志，承担两大核心作用：一是**保证事务原子性**，事务失败时根据 `undo log` 回滚数据；二是**维护 `MVCC` 版本链**，保存数据修改前的历史版本，供快照读查询使用。

## 3. bin log 二进制日志
`binlog` 是 MySQL 服务层日志，所有存储引擎通用，记录所有 `DDL`、`DML` 语句。核心作用是**主从复制、数据备份与恢复**，主库通过 `binlog` 同步数据到从库，同时可以通过 `binlog` 恢复误删、误改数据。

```sql
-- 查看binlog是否开启
SHOW VARIABLES LIKE '%log_bin%';
-- 查看binlog格式
SHOW VARIABLES LIKE 'binlog_format';
```

### 面试八股
**面试官提问：redoLog 和 binLog 的核心区别是什么？**

**口述回答**：第一层级不同，`redo_log` 是 `InnoDB` 引擎日志，`binlog` 是 MySQL 服务层日志；第二作用不同，`redo_log` 负责崩溃恢复、保证事务持久化，`binlog` 负责主从复制和数据恢复；第三日志类型不同，`redo_log` 是物理日志，记录磁盘数据页变化，`binlog` 是逻辑日志，记录 SQL 语句逻辑。

## 4. redo log 刷盘策略（WAL 机制）
MySQL 采用 **WAL（Write-Ahead Logging，先写日志、后写数据页）** 机制：事务提交时先保证 redo log 落盘，再异步把数据页刷入磁盘。即使数据页还没落盘就宕机，重启后也能根据 redo log 重做恢复，这就是"先写日志"的价值。

`innodb_flush_log_at_trx_commit` 参数控制 redo log 刷盘时机，是性能与安全的权衡：

| 取值 | 行为 | 安全性 | 性能 |
|---|---|---|---|
| 0 | 每秒刷盘一次，事务提交不主动刷 | 最不安全，最多丢1秒数据 | 最高 |
| 1（默认） | 每次事务提交都刷盘 | 最安全，不丢已提交数据 | 最低 |
| 2 | 每次提交只写入操作系统缓存，每秒刷盘 | 数据库崩溃不丢，操作系统宕机最多丢1秒 | 中 |

> 🎯【面试题】为什么说"事务提交即持久化"，但性能却不差？
> 参考答案：因为 redo log 是**顺序写**（追加日志），磁盘顺序写比数据页的**随机写**快几个数量级；数据页最终落盘是后台异步批量完成的。牺牲一点刷盘频率换取高吞吐，是典型的"顺序写换随机写"优化。

## 5. binlog 与 redo log 两阶段提交（2PC）
> 🎯【面试题】redo log 和 binlog 如何保证一致性？什么是两阶段提交？
> 参考答案：redo log 是引擎层日志（崩溃恢复用），binlog 是服务层日志（主从复制用），两者记录内容不同，如果不做协调，会出现"redo log 写了但 binlog 没写"或反之，导致崩溃恢复后的数据与从库不一致。InnoDB 通过**两阶段提交（2PC）** 协调：事务提交时先把 redo log 写入并标记为 **prepare 状态** → 写入 binlog → 再把 redo log 标记为 **commit 状态**。
> 如果崩溃发生在 prepare 后、binlog 写入前：回滚该事务；如果 binlog 已写入：即使 redo log 还是 prepare，也提交该事务（保证主从一致，因为从库会重放这条 binlog）。
> 一句话：**先 prepare redo log，再写 binlog，最后 commit redo log**，三步保证两套日志最终一致。

## 6. undo log 与 redo log 深度区别（面试高频）

> 🎯【面试题】undo log 和 redo log 都是 InnoDB 的日志，深度区别是什么？为什么二者缺一不可？
> 参考答案：一句话定位：**undo log 负责"撤销"（向后看），redo log 负责"重做"（向前看）**。
> - **记录内容不同**：undo 记录**逻辑逆操作**（INSERT 记反向 DELETE、UPDATE 记旧值），redo 记录**物理修改**（"某表空间某数据页某偏移改成了什么"）；
> - **为什么缺一不可**：只有 redo 没有 undo——事务执行一半失败无法回到修改前的状态，MVCC 也读不到历史版本；只有 undo 没有 redo——已提交事务的数据还在 Buffer Pool 未落盘，断电即丢，undo 是逻辑日志救不回已提交数据；
> - **日志性质不同**：redo 是**物理日志**，崩溃恢复直接按页重放，速度极快；undo 是**逻辑日志**，回滚相当于逻辑执行反向 SQL；
> - **写入方式不同**：redo **循环写**，空间固定、写满从头覆盖；undo 按回滚段循环使用，长事务会让旧版本大量堆积膨胀。
>
> **高频追问：redo 也要写磁盘，为什么不直接写数据页？**——**顺序 IO vs 随机 IO**：redo 是日志文件末尾追加的顺序写，性能接近内存；数据页修改要按 B+Tree 定位，是随机写，慢几个数量级。这正是 WAL"先写日志、后写数据页"的底层价值。

> ⚠️注意：undo log 本身也是数据，为防止 undo 丢失，**写 undo log 的操作同样会生成对应的 redo log**——相当于给"后悔药"也上了保险，答出这个细节是明显加分项。

## 7. binlog 误删数据恢复流程（面试高频）

> 🎯【面试题】误删数据怎么用 binlog 恢复？前提条件是什么？完整流程怎么走？
> 参考答案：前提：**binlog 已开启且 `binlog_format=ROW`**（ROW 记录每行变更前后完整值才能精准闪回，STATEMENT 只记 SQL 无法可靠逆向）。核心思路：**定位误操作区间 → 提取 binlog → 生成逆向 SQL → 重新执行**：
> 1. 确认状态：`SHOW VARIABLES LIKE 'log_bin'`、`SHOW VARIABLES LIKE 'binlog_format'`；
> 2. `SHOW BINARY LOGS` 按误操作时间定位目标 binlog 文件；
> 3. 用 `mysqlbinlog --start-datetime --stop-datetime -v --base64-output=DECODE-ROWS` 导出可读文本，找到误 DELETE/UPDATE 前后的 position；
> 4. 用 **`binlog2sql`**（最常用）或 **`MyFlash`**（美团开源）加 `-B`（Flashback）参数自动生成**逆向 SQL**：DELETE 转 INSERT、INSERT 转 DELETE、UPDATE 的 SET 与 WHERE 对调；
> 5. 人工检查逆向 SQL 无误后导入恢复：`mysql -u root -p test_db < rollback.sql`。

| 高频陷阱 | 说明与对策 |
|---|---|
| `DROP`/`TRUNCATE` 误操作 | 属于 **DDL**，ROW binlog 只记录"删表"动作、不记录表数据，**闪回无效**，只能靠**最近一次全量备份 + 备份时间点之后的 binlog 全部重放** |
| STATEMENT 格式难恢复 | 只记录 SQL 语句，语句含 `NOW()`/`RAND()` 或数据已变化时，逆向 SQL 无法精准定位原行 |
| 主从架构下主库误删 | 会瞬间同步到从库，发现后立即 `STOP SLAVE` 阻断重放，再从从库提取完整数据恢复 |

> **预防方案（加分项）**：生产 DML 必须走审批流、禁止手工直连；客户端配置 `--safe-updates`（强制 UPDATE/DELETE 必须带主键条件）；搭建一台**延迟从库**（延迟 1 小时同步），为发现误删争取抢救窗口。
> 一句话：**闪回靠 ROW 格式 binlog + 逆向 SQL 工具，DDL 误删只能全备重放，生产必须审批流 + 延迟从库双保险**。

# 六、锁机制（并发安全核心）
锁是数据库解决多事务并发竞争、保证数据一致性的核心机制。MySQL 锁体系非常完善，按照粒度分为全局锁、表级锁、行级锁，按照功能分为共享锁、排他锁，同时包含 `MDL` 锁、意向锁、间隙锁、临键锁等特殊锁，是面试重难点。

```sql
-- 手动加表共享读锁
LOCK TABLES `emp` READ;
-- 手动加表排他写锁
LOCK TABLES `emp` WRITE;
-- 释放表锁
UNLOCK TABLES;

-- 行级共享锁（当前读）
SELECT * FROM `emp` WHERE `id` = 1 LOCK IN SHARE MODE;
-- 行级排他锁（当前读）
SELECT * FROM `emp` WHERE `id` = 1 FOR UPDATE;

-- 查看死锁日志
SHOW ENGINE INNODB STATUS;
```

## 1. 锁粒度层级
锁粒度越大，加锁开销越小、并发性能越低；粒度越小，加锁开销越大、并发性能越高。优先级：全局锁 > 表锁 > 行锁。`InnoDB` 优先使用行锁，保证高并发能力。

## 2. 特殊锁详解
### 2.1 MDL 元数据锁
`MDL` 锁是系统自动维护的元数据锁，所有 `DML` 读写操作会自动加 `MDL` 读锁，所有 `DDL` 修改表结构操作会加 `MDL` 写锁。核心作用是**防止 `DML` 和 `DDL` 并发冲突**，避免表结构变更过程中数据读写错乱，是线上 `DDL` 卡死问题的根源。

### 2.2 意向锁
意向锁分为意向共享锁 `IS`、意向排他锁 `IX`，是表级辅助锁。核心作用是提升表锁与行锁共存时的检测效率，不需要遍历全表所有行锁，就能快速判断表是否存在行锁，极大优化锁检测性能。

## 3. InnoDB 行锁细分
`InnoDB` 行锁精准锁定索引行，细分三类：记录锁锁定单条索引记录；间隙锁锁定两条索引之间的空白区间，防止插入幻读；临键锁是记录锁+间隙锁的结合体，左开右闭区间，彻底杜绝当前读幻读，是 `RR` 隔离级别核心机制。

> ⚠️ 注意：如果查询条件不走索引，行锁直接升级为表锁，整表被锁住。

## 4. 死锁
死锁是多事务互相持有对方所需锁资源、互相无限等待的现象，必须同时满足四大条件：互斥、请求保持、不可剥夺、循环等待。MySQL 会自动检测死锁，回滚代价最小的事务解除阻塞。生产优化方案：统一 SQL 加锁顺序、缩短事务执行时间、避免长事务。

## 5. 全局锁与表级锁（特点与使用场景）

> 🎯【面试题】全局锁、表级锁分别是什么？各自的特点和使用场景？
> 参考答案：
> - **全局锁（Global Lock）**：给**整个数据库实例**加锁，典型命令 `FLUSH TABLES WITH READ LOCK`（FTWRL），加锁后全库进入**只读状态**，所有 DML、DDL 全部被阻塞。特点：锁范围最大、并发完全归零，只用于**全库一致性备份**等极少数场景；生产备份优先用 `mysqldump --single-transaction`（走 `MVCC` 快照，不阻塞业务写）；
> - **表级锁（Table Lock）**：一次锁住整张表，分**表级读锁（READ，共享）**与**表级写锁（WRITE，独占）**，遵循"读读共享、读写互斥、写写互斥"。特点：加锁开销小、不会产生死锁，但**锁粒度大、并发度极低**。使用场景：`MyISAM` 引擎只支持表锁（读快但写并发差）；`InnoDB` 业务表**禁止手动 `LOCK TABLES`**，否则整表读写被阻塞，`InnoDB` 高并发靠的是行锁 + `MVCC`。

```sql
-- 全局锁：全库只读（仅备份等极少数场景）
FLUSH TABLES WITH READ LOCK;
UNLOCK TABLES;

-- 表级读锁：本会话及其他会话都可读，不可写
LOCK TABLES `emp` READ;
-- 表级写锁：独占，阻塞其他所有读写
LOCK TABLES `emp` WRITE;
UNLOCK TABLES;
```

一句话：**全局锁锁整个库、表锁锁整张表，都是"粒度大、并发低"的兜底锁；`InnoDB` 日常并发靠行锁 + `MVCC`，表锁只属于 `MyISAM` 或临时维护操作**。

## 6. 共享锁与排他锁的互斥机制（读读共享、读写互斥）

> 🎯【面试题】共享锁（S 锁）与排他锁（X 锁）的互斥机制是什么？为什么读读能并发、读写必须互斥？
> 参考答案：核心口诀是**读读共享、读写互斥、写写互斥**，兼容矩阵如下：

| 锁类型 | S 共享锁 | X 排他锁 |
|---|---|---|
| S 共享锁 | ✅ 兼容，可同时持有 | ❌ 互斥，必须等 X 释放 |
| X 排他锁 | ❌ 互斥 | ❌ 互斥 |

> - **共享锁（读锁，S）**：多个事务可以同时对同一行加 S 锁并读取，**读读不阻塞**，这是 `InnoDB` 支撑高并发读的基石；
> - **排他锁（写锁，X）**：事务对数据加了 X 锁后，其他事务既不能加 X 锁也不能加 S 锁，直到持锁事务**提交或回滚释放**——保证写期间其他事务读不到"写了一半"的数据；
> - 加锁语法：`SELECT ... LOCK IN SHARE MODE` 加 S 锁；`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 自动加 X 锁；
> - **面试延伸**：两事务各自先持有对方所需数据的 S 锁、再都想升级为 X 锁，会互相等待形成**死锁**（死锁详见本章 §4）；持 X 锁的长事务是阻塞读写的最大元凶，必须尽快提交。

## 7. MDL 锁的阻塞机制与线上 DDL 卡死规避（面试高频）

> 🎯【面试题】`MDL` 元数据锁的阻塞机制是什么？线上 `DDL` 为什么会卡死？如何规避？
> 参考答案：`MDL` 加锁规则（承接上文 2.1）：所有 **DML 读写自动加 `MDL` 读锁**（读锁之间互相兼容），所有 **`DDL`（ALTER/DROP/TRUNCATE）需要 `MDL` 写锁**（与任何读锁、写锁都互斥）。
> **阻塞链条（线上 DDL 卡死全过程）**：
> 1. 一个**长事务/长查询**持有表的 `MDL` 读锁迟迟不提交；
> 2. `DDL` 要加 `MDL` 写锁，与读锁互斥，只能**排队等待**；
> 3. MySQL 的 `MDL` 等待队列**写优先**（防止写锁饿死），`DDL` 排队期间新来的 DML 读锁请求全部排在 `DDL` 后面；
> 4. 结果：**整张表的读写被连带阻塞**，`SHOW PROCESSLIST` 出现大量 `Waiting for table metadata lock`，表现为"表突然卡死、请求全部堆积"。
> **线上规避方案**：
> 1. 根治：消灭**长事务/长查询**——事务内不做远程调用、不跑慢 SQL，业务高峰期禁止大查询（长事务危害见 `# 九`）；
> 2. `DDL` 放**业务低峰期**执行，大表用 `pt-online-schema-change` / `gh-ost` 在线变更，MySQL 8.0 可加 `ALGORITHM=INSTANT`；
> 3. 设置 `lock_wait_timeout`（DDL 等待 `MDL` 超时自动放弃），避免无限期堆积拖垮连接池；
> 4. 应急排查：`SHOW PROCESSLIST` 找到持锁的长事务源头会话，`kill` 后 `DDL` 自动继续。
> 一句话：**`DDL` 卡死的本质是"长事务占 `MDL` 读锁不释放 → `DDL` 写锁排队 → 写优先导致后续 DML 全被堵死"，规避核心是别让长事务和 `DDL` 抢同一把 `MDL` 锁**。

## 8. 记录锁、间隙锁、临键锁深度辨析（面试高频）

> 🎯【面试题】记录锁、间隙锁、临键锁的加锁规则是什么？什么情况下会降级？间隙锁为什么不互斥？
> 参考答案：InnoDB 行锁本质是**加在索引项上**（没有单独的"行锁位"，就是在索引记录上打标记），三种锁算法在 `RR` 级别下配合使用：
> - **记录锁（Record Lock）**：锁单条**索引记录**本身。**主键/唯一索引等值查询且记录存在**时触发，此时临键锁会**降级为记录锁**（值唯一，不会再插入重复值，无需防幻读）；查询条件无索引时会对**全表所有记录**加锁，等效表锁；
> - **间隙锁（Gap Lock）**：锁索引记录之间的**空隙**（含第一条记录之前、最后一条记录之后），唯一目的是**禁止插入、防止幻读**，本身不锁任何记录。触发场景：**唯一索引等值查询但记录不存在**（如只有 5 和 10，查 7，临键锁降级为纯间隙锁 `(5,10)`）、非唯一索引查询、范围查询。**间隙锁之间不互斥**，多个事务可同时持有同一段间隙锁，它们共同的敌人只有一个——`INSERT`；
> - **临键锁（Next-Key Lock）**：记录锁 + 记录**左侧**间隙锁的组合，**左开右闭**区间如 `(5,10]`，是 **`RR` 级别的默认加锁算法**，同时解决"修改已有记录"和"插入新记录（幻读）"两类问题。

**加锁/降级规则速查**：

| 查询场景 | 加锁结果 | 原因 |
|---|---|---|
| 唯一索引等值，记录存在 | 记录锁 | 不会插入重复值，无需防幻读 |
| 唯一索引等值，记录不存在 | 间隙锁 | 没有记录可锁，只锁空隙防插入 |
| 非唯一索引等值，记录存在 | 两个临键锁（如 `(10,20]` + `(20,30)`） | 相同值可重复插入，须合围该值的整个取值区间 |
| 范围查询 | 范围内全部临键锁 + 右侧到正无穷 | 防止范围内任意位置插入 |

> **为什么非唯一索引等值要锁两个区间**：二级索引实际按 `(索引列, 主键)` 排序，`age=20` 的记录在索引中连续存储，新的 `age=20`（id 更大）会插在现有记录**之后**、下一个值 `30` 之前。`(10,20]` 挡住前面的插入，`(20,30)` 挡住后面的插入，两段合围才能真正杜绝幻读；只锁一边，对方从另一侧插入同样会产生幻影行。
> ⚠️注意：间隙锁不互斥是**死锁重灾区**——事务 A、B 同时持有 `(5,10)` 间隙锁后互相往里 INSERT，插入意向锁被对方的间隙锁阻塞，互相等待形成死锁；**DELETE/UPDATE 不存在的记录同样会加间隙锁**，线上大量"删除不存在记录"的并发操作是高频死锁场景。`RC` 级别没有间隙锁、临键锁，只加记录锁，并发更高但防不住幻读。
> 补充一个幻读残留场景：事务 A 先快照读未见某行 → 事务 B 插入并提交 → A 用 `UPDATE`（当前读）能改到这行 → A 再快照读就能看见它了。所以 `RR` 的"彻底解决"指业务层面，极端交错场景仍有幻读窗口。
> 一句话：**RR 默认临键锁（左开右闭），唯一索引等值命中降级记录锁、未命中降级间隙锁；间隙锁彼此兼容但都挡 INSERT，这是防幻读的代价，也是死锁的源头**。

## 9. 两个事务 UPDATE 同一行数据的阻塞问题（面试高频）

> 🎯【面试题】两个事务同时 UPDATE 同一行会怎样？锁什么时候释放？阻塞太久会发生什么？
> 参考答案：**会阻塞**。UPDATE 是当前读，执行前必须先拿到该行的 **X 排他锁**，X 锁互斥，后来者只能排队等待：
> - **加锁**：事务 A `UPDATE ... WHERE id=1` 先执行，获得 `id=1` 行的 X 锁；事务 B 执行同样语句时发现 X 锁被占用，进入**锁等待（Lock Wait）**被挂起；
> - **释放时机（关键）**：遵循**两阶段锁协议（2PL）**——事务执行过程中获得的锁，**不是语句执行完就释放**，而是**统一持有到事务 COMMIT / ROLLBACK 时才一次性释放**。所以 A 执行完 UPDATE 但不提交，B 会一直阻塞，"长事务持有行锁"是线上阻塞的最大元凶；
> - **阻塞超时**：等待超过 `innodb_lock_wait_timeout`（默认 **50 秒**）后报错 `Lock wait timeout exceeded`；
> - **互相等待即死锁**：A 锁行 1 等行 2、B 锁行 2 等行 1，InnoDB 通过 **wait-for graph 等待图**做死锁检测，瞬间发现并**回滚代价较小的事务**打破循环；
> - **无索引放大灾难**：WHERE 条件无索引或索引失效时全表扫描，会给**所有行**加锁，其他事务更新任何一行都被阻塞，等效表锁。

> ⚠️注意：UPDATE 未提交期间，其他事务的**普通 SELECT（快照读）不受阻塞**，走 MVCC 读旧版本；被阻塞的是 `FOR UPDATE`、`UPDATE`、`DELETE` 这类当前读/写操作——正是"读写不冲突、写写必互斥"。
> **优化方向**：确保 UPDATE 走索引缩小锁范围、缩短事务尽快提交、热点行并发用 Redis 分布式锁或消息队列削峰挡在数据库之外；MySQL 8.0 可用 `FOR UPDATE NOWAIT`（抢不到锁立即报错）和 `FOR UPDATE SKIP LOCKED`（跳过被锁行，适合任务领取场景）。
> 一句话：**同行 UPDATE 必排队，锁的生死边界是事务提交而非语句结束（2PL），控制锁的持有时间就是控制并发能力**。

# 七、索引底层原理与优化（面试高频）
索引是数据库优化的核心，所有慢查询、接口卡顿、数据库性能瓶颈，90% 都和索引设计不合理、索引失效有关。面试重点考察 `B+Tree` 底层、聚簇非聚簇索引、覆盖索引、索引失效、优化方案。

```sql
-- 创建普通单列索引
CREATE INDEX idx_emp_name ON `emp`(`name`);

-- 创建联合索引（最左前缀）
CREATE INDEX idx_emp_sal_dept ON `emp`(`salary`,`dept_id`);

-- 创建唯一索引
CREATE UNIQUE INDEX idx_emp_phone ON `emp`(`phone`);

-- 查看表索引
SHOW INDEX FROM `emp`;

-- 执行计划分析SQL，必看type列
EXPLAIN SELECT * FROM `emp` WHERE `name`='张三';
```

## 1. B+Tree 索引优势
MySQL 默认使用 `B+Tree` 作为索引结构，相比 `B` 树，`B+Tree` 非叶子节点只存储索引键、不存储数据，树的层级更低、磁盘 IO 更少；所有数据都在叶子节点，叶子节点双向链表串联，范围查询、排序查询效率极高。相比 `Hash` 索引，支持范围查询、排序、分组，数据稳定无哈希冲突。

**B+Tree 层高与容量计算（面试高频）：**
MySQL 默认数据页大小 16KB，非叶子节点只存索引键+子节点指针。假设主键 bigint 占 8 字节、指针占 6 字节，一个页可存 `16KB / 14 ≈ 1170` 个索引项；叶子节点存数据行，假设一行 1KB，一页可存 16 行。
- 2 层 B+Tree：`1170 × 16 ≈ 1.8万` 行；
- 3 层 B+Tree：`1170 × 1170 × 16 ≈ 2100万` 行；
- 4 层 B+Tree：`1170³ × 16 ≈ 256亿` 行。
> 结论：**3 层 B+Tree 就能支撑千万级数据量**，意味着千万级表查询最多 3 次磁盘 IO，这就是 B+Tree 让 MySQL 支撑海量数据的关键。

## 2. 聚簇索引与非聚簇索引
聚簇索引就是主键索引，叶子节点直接存储整行完整数据，查询速度最快；非聚簇索引是普通二级索引，叶子节点只存储主键值，查询到数据后需要根据主键再次回表查询完整数据，产生二次 IO，也就是**回表查询**。

## 3. 覆盖索引
覆盖索引是优化天花板，当查询的所有字段都包含在二级索引中，不需要回表查询，直接从索引获取数据，省去二次 IO，性能极致提升。日常优化优先设计覆盖索引，避免回表。

```sql
-- 建立联合索引，形成覆盖索引，不需要回表
CREATE INDEX idx_name_salary ON `emp`(`name`,`salary`);
-- extra列出现Using index，代表命中覆盖索引
EXPLAIN SELECT `name`,`salary` FROM `emp` WHERE `name`='张三';
```

## 4. 索引失效全集
索引列使用函数运算、隐式类型转换、左侧模糊匹配、`or` 连接无索引字段、违反最左前缀法则、`order by` 字段无索引、`null` 判断不当，都会直接导致索引失效，走全表扫描。

```sql
-- 索引失效示例1：索引列做函数运算
EXPLAIN SELECT * FROM `emp` WHERE DATE(create_time) = '2026‑08‑25';

-- 索引失效示例2：左侧模糊匹配
EXPLAIN SELECT * FROM `emp` WHERE `name` LIKE '%三';

-- 索引失效示例3：隐式类型转换，字符串字段传数字
EXPLAIN SELECT * FROM `emp` WHERE `phone` = 13800138000;
```

## 5. explain 执行计划
`explain` 用于分析 SQL 执行效率，核心看 `type` 字段，性能从高到低：`system > const > eq_ref > ref > range > index > ALL`，开发必须杜绝 `ALL` 全表扫描。

**explain 核心字段详解：**
| 字段 | 含义 | 关注点 |
|---|---|---|
| id | 查询编号，值越大越先执行 | 相同id按顺序执行 |
| select_type | 查询类型：SIMPLE简单查询、PRIMARY最外层、SUBQUERY子查询、DERIVED派生表 | 复杂查询关注 |
| table | 访问的表名 | - |
| type | 访问类型，性能从好到差：`system > const > eq_ref > ref > range > index > ALL` | **重点关注，杜绝ALL** |
| possible_keys | 可能用到的索引 | 是否有索引可选 |
| key | 实际使用的索引 | 是否用上最优索引 |
| key_len | 使用的索引长度 | 联合索引可判断用到了几个字段 |
| rows | 预估扫描行数 | 越小越好 |
| Extra | 额外信息：`Using index`覆盖索引（最优）、`Using where`、`Using filesort`文件排序（需优化）、`Using temporary`临时表（需优化）、`Using index condition`索引下推 | 出现filesort/temporary要警惕 |

> 优化判断口诀：**type 尽量到 range 及以上，rows 尽量小，Extra 不要出现 filesort/temporary**。

## 6. 索引下推 ICP 与 MRR 优化
> 🎯【面试题】什么是索引下推（ICP）？
> 参考答案：ICP（Index Condition Pushdown）把 where 中**能用索引判断的过滤条件下推到存储引擎层**，在回表之前先过滤，减少回表次数。典型场景：联合索引`(name, age)`，查询`WHERE name LIKE '张%' AND age > 18`，没有ICP需要把所有匹配"张%"的记录全部回表再过滤age；有ICP先在索引层判断age>18，只对通过的记录回表。

> 🎯【面试题】什么是MRR？
> 参考答案：MRR（Multi-Range Read，多范围读）把回表的主键值先排序再批量回表，把随机IO变成顺序IO，减少磁盘寻道次数，提升回表性能。适合二级索引查询大量记录需要回表的场景。

## 7. 前缀索引
> 🎯【面试题】什么是前缀索引？什么时候用？
> 参考答案：对字符串字段只取前N个字符建索引，`CREATE INDEX idx_name ON emp(name(10))`。适用场景：字段很长（邮箱、URL、身份证等）且区分度高的前缀，能大幅缩小索引体积、减少磁盘IO。缺点：无法使用覆盖索引（索引里存的不是完整值）；排序、分组无法完全利用索引；必须根据**区分度**选择合适长度：`SELECT COUNT(DISTINCT LEFT(column, n)) / COUNT(*)` 计算前缀区分度，通常达到 0.9 以上即可。

## 8. 索引设计最佳实践（什么时候建索引）
**应该建索引的场景：**
- where 条件频繁使用的字段；
- order by / group by / join 关联字段（on后面的字段）；
- 区分度高的字段优先（性别这种区分度低的字段建索引收益极小）；
- 联合索引遵循最左前缀，高频字段放最左。

**不建议建索引的场景：**
- 数据量很小的表（全表扫描比走索引更快）；
- 频繁更新的字段（索引维护成本高，每次更新都要改B+Tree）；
- 区分度极低的字段（如性别、状态位）；
- 大文本/大字段不能直接建索引（需前缀索引或全文索引）；
- 索引不是越多越好，每张表建议控制在5个以内，索引会拖慢写入性能、占用磁盘空间。

## 9. ORDER BY / GROUP BY 排序优化（filesort）
> 🎯【面试题】order by 什么时候走索引？什么是Using filesort？
> 参考答案：order by 字段如果恰好命中索引顺序（联合索引与排序字段顺序一致、方向一致），MySQL直接按索引顺序读取，无需额外排序；如果无法利用索引排序，就会生成临时排序文件做**filesort**，数据量大时性能极差。GROUP BY、DISTINCT 同理，优先走索引。

**优化手段：**
1. 排序字段建索引，且**联合索引顺序与 order by 字段顺序一致**（如索引`(a,b)`支持`ORDER BY a,b`，不支持`ORDER BY b,a`）；
2. 排序方向一致：`ORDER BY a DESC` 可走索引（MySQL8支持降序索引），但`ORDER BY a ASC, b DESC`混合方向会filesort；
3. 尽量只查需要的字段，避免`select *`导致filesort要处理大字段；
4. 排序数据量大时增大`sort_buffer_size`，或利用覆盖索引避免回表；
5. 深分页排序场景（`ORDER BY create_time LIMIT 100000,20`）配合延迟关联/游标分页。

## 10. 联合索引最左前缀法则（底层原理详解）

> 🎯【面试题】最左前缀法则的底层原理是什么？为什么跳过前置列索引就失效？
> 参考答案：联合索引（如 `(name, age, dept_id)`）底层**仍然是一棵 B+Tree**，但叶子节点的排序规则是：**先按第一列排序，第一列相同再按第二列排序，第二列相同再按第三列排序**，逐列递进。因此：
> - 只有 **第一列确定**时，第二列才在索引中"局部有序"，能继续用索引定位；
> - 只有 **前两列都确定**时，第三列才有序；
> - 一旦**跳过前置列直接查后面的列**（如 `WHERE age = 25`），跳过的列在整棵树上**整体无序**，无法二分定位，只能退回全表/全索引扫描——这就是最左前缀法则的底层原因。

```sql
-- 联合索引：(name, age, dept_id)
EXPLAIN SELECT * FROM `emp` WHERE `name`='张三' AND `age`=25;     -- 命中 name+age 两列
EXPLAIN SELECT * FROM `emp` WHERE `name`='张三' AND `dept_id`=1;  -- 中间跳过 age，只有 name 走索引
EXPLAIN SELECT * FROM `emp` WHERE `age`=25;                       -- 跳过最左列 name，索引整体失效
```

> 补充：MySQL 8.0 的 **Skip Scan（跳跃扫描）** 在"最左列区分度低"等少数场景能让跳列查询部分走索引，但限制多、不能依赖；业务上仍必须遵守最左前缀。
> 一句话：**最左前缀 = 联合索引的列在 B+Tree 里从左到右逐级有序，用索引必须从最左边连续起步，跳列必失效**。

## 11. 索引失效场景汇总：隐式类型转换为何导致失效（面试高频）

> 🎯【面试题】索引失效场景有哪几类？隐式类型转换为什么会导致索引失效？
> 参考答案：失效场景全汇总：

| 失效场景 | 典型写法 | 解决思路 |
|---|---|---|
| 索引列参与函数/运算 | `WHERE DATE(create_time)='2026-08-25'` | 改写为范围查询 `create_time >= ? AND create_time < ?` |
| **隐式类型转换** | 字符串列 `phone` 与数字 `13800138000` 比较 | 字段与参数类型一致，字符串必须加引号 |
| 左侧模糊匹配 | `WHERE name LIKE '%三'` | 改前缀匹配 `'三%'`，或前缀索引/全文索引 |
| `or` 连接无索引字段 | `WHERE name='a' OR status=1` | 两侧都有索引，或拆 `UNION` |
| 违反最左前缀法则 | 联合索引 `(name,age)` 但 `WHERE age=25` | 从最左列连续使用（见本章 §10） |
| 范围查询右侧列失效 | `WHERE age>18 AND dept_id=1` | 范围列尽量放联合索引最后，右侧列另建索引 |
| 负向条件/`null` 判断不当 | 大范围 `NOT IN`、`<>`、`IS NULL` | 避免负向查询，必要时用 `EXISTS` |

> **隐式类型转换原理（重点）**：MySQL 比较时，若一侧是数字、一侧是字符串，会**把字符串转换为数字**参与比较。当被转换的是**索引列**（`phone = 13800138000` 等价于对列做 `CAST(phone AS SIGNED)`），每一行都要先转换列值，转换结果与 B+Tree 中已排好序的**原始字符串键无法有序对照**，优化器只能放弃索引走全表扫描；反之数字列 `id = '1'`，转换发生在常量侧，索引列未被加工，索引依然可用。
> 生产规范：**字段类型与查询参数类型严格一致，字符串列查询必须加引号，从源头杜绝隐式类型转换**。

## 12. InnoDB 页分裂机制（面试高频）

> 🎯【面试题】什么是页分裂？什么情况下发生？为什么强烈推荐自增主键？
> 参考答案：页分裂（Page Split）指**数据页（16KB）已写满，新记录又要插入到该页中间位置**时，InnoDB 为维持 B+Tree 有序性，把原页**后半部分数据搬到新页**的过程，本质是用空间碎片和额外 IO 换取索引有序：
> - **顺序追加（理想状态）**：自增主键总在最后一个页的末尾插入，页满了直接开辟新页，无任何旧数据搬移，效率最高；
> - **中间插入（触发分裂）**：某页已满存着 `[1,2,3,5,6]`，此时插入 4——必须新开一页，把 5、6 搬过去再插入 4，一个满页变成两个**约 50% 填充率的半满页**，同时上层节点要更新指针，还可能**级联分裂导致树长高一层**；
> - **三大代价**：写性能下降（额外 IO）、空间碎片（填充率骤降）、逻辑相邻的数据物理分散（范围查询变成随机 IO）。

**触发场景**：主键非自增（UUID、随机字符串最典型，新主键随机落进已写满的中间页）；业务主键"插队"式插入；VARCHAR 大字段更新变长导致当前页装不下。

> 有分裂就有**页合并（Page Merge）**：删除数据或更新缩短后，相邻两页填充率都低于约 50% 时，InnoDB 会把两页合并为一页回收空间。
> 优化方案：**自增整型主键（第一准则）**、主键尽量短（同时缩小所有二级索引体积）、碎片严重时 `OPTIMIZE TABLE` 重建表整理。
> 一句话：**页分裂 = "页满 + 非末尾插入"，UUID 主键随机插入频繁分裂拖垮写入性能，自增主键让数据永远尾部追加是第一保命实践**。

## 13. 索引越大 B+ 树越高的量化原因（面试高频）

> 🎯【面试题】为什么索引字段越大 B+ 树越高？能定量分析吗？
> 参考答案：核心公式 **`树高 H ≈ log_M(N)`**（N 为总行数，M 为扇出），N 不变时 **M 越小树越高**，而 M 由"页大小 ÷ 单个索引项大小"决定：
> - bigint 主键 8 字节 + 指针 6 字节 = 14 字节，16KB 页可存约 **1170** 个索引项（承接本章 §1）；若索引键是 100 字节的长字符串，100 + 6 = 106 字节，一页只能存约 **150** 个；
> - 扇出缩小直接"吃掉"每层容量（叶子按每页 16 行折算，与 §1 口径一致）：

| 树高 | bigint 主键（扇出≈1170） | 100 字节长键（扇出≈150） |
|---|---|---|
| 2 层 | ≈1.9 万行 | ≈2400 行 |
| 3 层 | ≈2100 万行 | ≈36 万行 |
| 4 层 | ≈256 亿行（基本用不满） | ≈5.4 亿行 |

> - 同样 **1000 万行**数据：bigint 主键 3 层绰绰有余；长字符串键 3 层只能装 36 万行，必须长到**第 4 层**，树每多一层查询就多一次磁盘 IO；
> - **物理后果**：3 层时根节点和第二层基本常驻内存，实际 1~2 次 IO；树长到 5 层，内存装不下上层节点，IO 次数上升，响应时间直接翻倍。
> 一句话：**索引变大 → 单页存的索引项变少 → 扇出变小 → 同样数据量树只能往高长 → IO 变多。前缀索引、整型自增主键、主键宜短不宜长，本质都是在"把树压扁、减少 IO"**。

## 14. MySQL 与 MongoDB 索引结构对比（B+ 树 vs B 树）

> 🎯【面试题】MySQL 为什么用 B+ 树，MongoDB 为什么用 B 树？为什么不用二叉树、红黑树？
> 参考答案：**业务场景决定数据结构选型**，核心是"范围查询 vs 点查询"：
> - **为什么不用二叉树/红黑树**：二叉结构太"高瘦"，千万级数据树高可达 20 层以上，每层一次磁盘 IO，性能灾难；B+ 树多叉矮胖，把树高压到 3~4 层（见本章 §1、§13）；
> - **MySQL（关系型，B+ 树）**：大量范围查询、排序、分组需求。非叶子节点只存键值，单页容纳更多索引项、树更矮；数据全在叶子节点且叶子间**双向链表**串联，范围查询定位起点后顺链表顺序遍历即可；任何查询都要走到叶子，**IO 次数稳定可预期**；全表扫描沿叶子链表顺序完成；
> - **MongoDB（文档型，B 树）**：典型场景是按 `_id` 拉取整个文档的**单点查询**。B 树每个节点（含内部节点）都存数据，命中根节点或靠近根的内部节点可直接返回，**平均查询路径更短**，对范围遍历依赖弱。
>
> ⚠️注意：两个加分陷阱——MongoDB 默认的 **WiredTiger 引擎磁盘存储实际也是 B+ 树变体**（叶子同样有链表结构），"MongoDB 用 B 树"是经典教材说法，能指出技术演进是亮点；切忌脱离场景说"B 树比 B+ 树快"，脱离范围查询与点查场景的比较毫无意义。
> 一句话：**B+ 树为"范围扫描 + 稳定 IO"而生（MySQL），B 树为"单点命中即返回"而生（MongoDB），索引选型跟着查询模式走**。

# 八、数据库引擎对比
MySQL 主流两大存储引擎为 `InnoDB` 和 `MyISAM`，`InnoDB` 是默认引擎、适配高并发业务，`MyISAM` 适配静态只读场景。`InnoDB` 支持事务、行锁、`MVCC`、崩溃恢复、外键，并发性能高、数据安全；`MyISAM` 不支持事务、仅表锁、无事务机制，读取速度快，但不适合高并发读写业务。

```sql
-- 查看表使用引擎
SHOW CREATE TABLE `emp`;
-- 修改表引擎
ALTER TABLE `emp` ENGINE=InnoDB;
```

## 1. InnoDB 与 MyISAM 全面对比（面试高频）

> 🎯【面试题】InnoDB 和 MyISAM 全方位对比？两者底层索引实现有什么差异？
> 参考答案：MySQL 5.5 之后 **InnoDB 是默认引擎**，互联网业务基本无脑选 InnoDB，核心差异：

| 对比维度 | InnoDB | MyISAM | Memory |
|---|---|---|---|
| 事务 | 支持（ACID 完整） | 不支持 | 不支持 |
| 锁粒度 | 行级锁，高并发表现极佳 | 表级锁，并发写性能断崖式下跌 | 表级锁 |
| 外键 | 支持 | 不支持 | 不支持 |
| 崩溃恢复 | 支持（redo log，Crash-safe） | 不支持，断电可能表损坏 | 重启数据全丢 |
| MVCC | 支持 | 不支持 | 不支持 |
| 索引结构 | **聚簇索引**：主键索引叶子直接存**整行数据** | 索引与数据分离，叶子存**数据物理地址**，需按地址二次查找 | 哈希/B+树，数据全在内存 |
| `count(*)` | 需扫描（MVCC 下不同事务可见行数不同，无法维护总行数） | 维护了总行数变量，无 where 时直接返回、极快 | - |
| 适用场景 | 绝大多数在线业务 | 只读报表、静态数据（如今极少） | 临时表、中间结果 |

> **索引实现差异（追问重点）**：InnoDB 主键索引即数据本身（聚簇），二级索引叶子存**主键值**，命中后还要回表；MyISAM 所有索引叶子都存**物理地址**，不存在"回表"概念但多一次地址寻址。
> ⚠️注意：存储引擎是**表级别**配置，同一库中不同表可用不同引擎（不推荐）；InnoDB 行锁加在索引上，无索引查询退化为全表加锁——高频线上事故根源（见 `# 六`）。
> 一句话：**InnoDB 靠"事务 + 行锁 + MVCC + 崩溃恢复"四大能力统治在线业务，MyISAM 只剩只读静态场景的残值，生产无特殊理由一律 InnoDB**。

## 2. SQL 与 NoSQL 的区别与选型（面试高频）

> 🎯【面试题】SQL 关系型数据库和 NoSQL 的区别是什么？业务系统怎么选型？
> 参考答案：SQL 追求**强一致性、完整性与复杂关联查询**（ACID），NoSQL 追求**高并发、海量存储、横向扩展与模式灵活**（BASE），四个维度对比：

| 维度 | SQL（MySQL 等） | NoSQL（Redis/MongoDB/HBase 等） |
|---|---|---|
| 数据模型 | 固定表结构，先定义 schema，字段强约束，支持外键强关联 | 动态模式，KV（Redis）、文档（MongoDB）、列族（HBase）、图（Neo4j），同集合文档字段可以不同 |
| 事务 | ACID 强一致，转账、扣库存必备 | 多为 **BASE 理论**：基本可用（Basically Available）、软状态（Soft State）、最终一致（Eventually Consistent） |
| 扩展性 | 传统纵向扩容，分库分表可实现但复杂度高 | 天生分布式，加廉价节点水平扩容（Scale-out） |
| 查询能力 | 标准 SQL，复杂 JOIN、聚合分析强大 | 各自独立的 API/查询语法，多表关联支持弱或没有 |

> **选型口诀**：核心交易链路（订单、支付、账务）用 SQL，保证金额分毫不差；高并发读、海量非结构化数据（商品详情、评价、浏览轨迹、IoT 上报）用 NoSQL。现代架构普遍**多存储共存（Polyglot Persistence）**：MySQL 存核心数据 + Redis 做缓存 + ES 做检索 + MongoDB 存文档，各司其职。
> ⚠️注意：两个陷阱——不要说"NoSQL 都不支持事务"（MongoDB 4.0+ 已支持多文档事务，只是能力弱于关系库）；也不要说"MySQL 扛不住大数据"（配合索引优化与分库分表，TB 级依然稳健）。NoSQL 的核心优势在于**扩展性与灵活性**，而不仅仅是"快"。

# 九、线上高阶优化方案
深分页 `limit 10000,10` 会扫描大量无效数据，优化方案为主键覆盖索引分页、延迟关联；`count(*)` 统计行数最准确，`count(字段)` 忽略 `null` 值统计不准；长事务会堆积 `undo_log`、占用锁、引发主从延迟，必须拆分缩短事务；日常开发杜绝 `select *`、规避索引失效、合理设计联合索引、遵守最左前缀法则。

```sql
-- 深分页原始慢SQL
SELECT * FROM `emp` LIMIT 10000,10;

-- 优化方案1：主键子查询（覆盖索引）
SELECT * FROM `emp` WHERE `id` >= (SELECT `id` FROM `emp` LIMIT 10000,1) LIMIT 10;

-- 优化方案2：延迟关联
SELECT e.* FROM `emp` e
INNER JOIN (SELECT `id` FROM `emp` LIMIT 10000,10) t ON e.`id` = t.`id`;
```

**慢查询日志与线上排查：**
```sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;            -- 超过1秒的SQL记录
SHOW VARIABLES LIKE 'slow_query_log%';
-- 查看当前正在执行的SQL（排查卡死/长事务）
SHOW PROCESSLIST;
```
排查步骤：开启慢查询日志 → 定位慢SQL → `EXPLAIN`分析执行计划 → 检查索引/改写SQL → 压测验证。

**count(*) 与 count(1)、count(字段) 的区别（面试高频）：**
| 写法 | 统计内容 | 说明 |
|---|---|---|
| `count(*)` | 统计所有行数 | 性能最好，**统计行数必须用它** |
| `count(1)` | 统计所有行数 | 与count(*)基本等价，不取字段值 |
| `count(字段)` | 统计该字段**非NULL**的行数 | 会忽略NULL，业务统计不准的常见坑 |
> 注意：count(*) 不统计被标记删除的行；超大表count依然慢，可用近似值（information_schema统计信息）或缓存计数。

# 十、MySQL 架构与一条 SQL 的执行流程（底层基础）
> 🎯【面试题】一条SQL在MySQL中是怎么执行的？
> 参考答案：MySQL整体分两层——**Server层**（连接器、查询缓存、分析器、优化器、执行器，所有引擎共用）和**存储引擎层**（InnoDB/MyISAM，负责数据存储与读写）。一条查询SQL的执行链路：
> 1. **连接器**：校验用户名密码、建立连接、管理连接池；
> 2. **查询缓存**：命中缓存直接返回（MySQL8.0已移除该模块，因为表一更新缓存就失效，弊大于利）；
> 3. **分析器**：词法分析（拆解SQL关键字、表名、字段）+ 语法分析（校验语法，报"语法错误"就在这里）；
> 4. **优化器**：决定执行方案——选哪个索引、join顺序、是否走索引下推，生成执行计划；
> 5. **执行器**：调用存储引擎接口逐行读取数据，返回结果集。

一条更新SQL（UPDATE）与查询的区别：执行器改内存数据 → 写 undo log（记录旧值）→ 写 redo log（prepare）→ 写 binlog → redo log commit，最终两阶段提交完成。

## 1. SQL 编写顺序与真实执行顺序（面试高频）

> 🎯【面试题】SQL 的编写顺序和执行顺序一样吗？为什么 WHERE 里不能用 SELECT 定义的别名？
> 参考答案：完全不同。**口诀：先找表（FROM）→ 过滤（WHERE）→ 分组（GROUP BY）→ 组过滤（HAVING）→ 选列（SELECT）→ 去重（DISTINCT）→ 排序（ORDER BY）→ 截取（LIMIT）**：

| 执行顺序 | 关键字 | 说明 |
|---|---|---|
| 1 | FROM | 锁定数据源，多表先做连接（笛卡尔积/JOIN） |
| 2 | ON | 应用连接条件，过滤不匹配的行 |
| 3 | JOIN | 外连接在此步补回保留表缺失的行（填 NULL） |
| 4 | WHERE | 行级过滤原始数据，**不能使用聚合函数** |
| 5 | GROUP BY | 划分分组，聚合计算的前提 |
| 6 | HAVING | 对分组后的小组二次过滤，**可以使用聚合函数** |
| 7 | SELECT | 确定输出列、计算表达式与别名 |
| 8 | DISTINCT | 结果集去重 |
| 9 | ORDER BY | 最终排序，最耗资源 |
| 10 | LIMIT | 截取最终返回的行数 |

> 由执行顺序直接推出三个高频结论：
> - **别名可用性**：`WHERE` 执行在 `SELECT` **之前**，别名还没诞生，所以 WHERE 中不能用 SELECT 定义的别名；`ORDER BY`、`LIMIT` 执行在 SELECT **之后**，可以用别名；
> - **WHERE 优先于 HAVING**：能用 WHERE 过滤的不要写 HAVING——WHERE 在分组前减少进入 GROUP BY 的数据量，HAVING 是分组后的"后过滤"，效率低；
> - **深分页慢的根源**：`LIMIT 1000000,10` 排序完成后已扫过前 100 万行再丢弃，必须配合游标分页（`WHERE id > 上一页最大id LIMIT 10`）或延迟关联根治（方案见 `# 九`）。
> ⚠️注意：`GROUP BY` 后 `SELECT *` 在严格模式下直接报错——非聚合列的归属不确定；开发原则一句话：**越早过滤越好，让参与分组和排序的数据量最小**。

## 2. 一条 UPDATE 语句的完整执行流程（必背）

> 🎯【面试题】`UPDATE user SET name='张三' WHERE id=1;` 在 MySQL 内部完整经历了什么？
> 参考答案：以 InnoDB 为例，完整链路八步，核心是 **Buffer Pool 内存操作 + 三大日志协同 + 两阶段提交**：
> 1. **加载数据页**：执行器请引擎取 `id=1` 的行，InnoDB 先查 **Buffer Pool**，该页不在则从磁盘加载进缓冲池；
> 2. **写 undo log**：修改前把旧值（`name='李四'`）写入 undo log，用于回滚和 MVCC 版本链；
> 3. **修改内存**：在 Buffer Pool 中把 `name` 改为'张三'，该页变为**脏页**（内存与磁盘不一致）；
> 4. **写 redo log（prepare）**：把"某数据页做了什么物理修改"写入 redo log buffer 并按策略刷盘，redo log 处于 **prepare** 状态；
> 5. **写 binlog**：执行器生成 binlog 并写入（提交成功后从库靠它同步）；
> 6. **提交（redo log commit）**：binlog 写完后，把 redo log 标记为 **commit**，两阶段提交闭环，事务真正完成；
> 7. **异步刷脏页**：Buffer Pool 的脏页不立即落盘，由后台线程按 **Checkpoint 机制**择机刷盘——系统空闲时、Buffer Pool 内存不足淘汰脏页时、**redo log 快写满时（最紧急，会阻塞所有更新全力刷盘）**、正常关闭时；
> 8. **崩溃恢复兜底**：若脏页刷盘前宕机，重启后按 redo log 重做未落盘的修改、按 undo log 回滚未提交事务，数据不丢不错。

> ⚠️注意：为什么脏页敢延迟刷盘？——只要 redo log 已落盘（WAL），数据页随时可以重做恢复；redo 是顺序写、脏页是随机写，延迟合并刷盘正是"顺序写换随机写"的性能来源（承接 `# 五` §4）。
> 一句话：**UPDATE = 改内存成脏页 + undo 保回滚 + redo(prepare)→binlog→redo(commit) 两阶段提交保一致 + Checkpoint 异步刷脏页**。

# 十一、InnoDB 存储引擎架构（Buffer Pool）
> 🎯【面试题】Buffer Pool是什么？为什么InnoDB读数据快？
> 参考答案：Buffer Pool（缓冲池）是 InnoDB 在内存中维护的一大块区域，缓存数据页、索引页、undo页，是 InnoDB 性能的核心。读写数据优先操作缓冲池，通过 `innodb_buffer_pool_size` 配置（生产建议设为物理内存的 60%~70%）。数据以**页（Page，默认16KB）**为单位加载：读数据先看缓冲池，没有再从磁盘加载并缓存；写数据先改缓冲池，标记为脏页，由后台线程异步刷盘，这就是"写缓冲、延迟落盘"。

**缓冲池配套机制：**
- **Change Buffer（写缓冲）**：二级索引页不在缓冲池时，不立即读盘，而是先记录变更，等该页被读到缓冲池时再合并应用，减少随机读盘；**唯一索引不能使用**（必须立即判断唯一性）；
- **自适应哈希索引 AHI**：InnoDB根据热点查询自动为频繁访问的索引页建立哈希索引，加速等值查询（无需人工干预）；
- **LRU淘汰**：缓冲池按LRU（最近最少使用）算法淘汰冷数据页；
- **预读（Read Ahead）**：检测到顺序访问趋势时，提前把相邻页加载进缓冲池。

> 补充：`SHOW ENGINE INNODB STATUS` 可以查看缓冲池命中率（Buffer pool hit rate），命中率低说明内存配置偏小或SQL扫描了大量无用的页。

## 1. Buffer Pool 三大链表与改良版 LRU（面试高频）

> 🎯【面试题】Buffer Pool 内部如何管理数据页？为什么 InnoDB 的 LRU 要分 young/old 两个区域？
> 参考答案：Buffer Pool 内部用三条链表管理缓存页（每页 16KB）：
> - **Free List（空闲链表）**：记录空闲缓存页，从磁盘读入新页时先从这里找空位；
> - **Flush List（脏页链表）**：记录被修改过的页（内存与磁盘不一致），后台刷盘线程按它刷脏页；
> - **LRU List**：管理页的冷热分层与淘汰。
>
> **普通 LRU 的致命问题——缓存污染**：一次全表扫描会把大量"只用一次"的页灌进 LRU 头部，把真正的热点页全部挤出去，缓存命中率瞬间暴跌。
> **InnoDB 的改良——分区 LRU**：整条链表按约 **63% young 区（热数据）+ 37% old 区（冷数据）** 划分：
> 1. 新读入的页先放入 **old 区头部**；
> 2. 在 old 区停留超过 `innodb_old_blocks_time`（默认 **1 秒**）后**再次被访问**，才晋升到 young 区头部；
> 3. 全表扫描的页只被访问一次、存活不到 1 秒，在 old 区就被淘汰，**保护 young 区热点数据不被冲掉**。

> 一句话：**分区 LRU = "新页先进 old 区观察 1 秒，二次访问才转正"，用极小代价挡住全表扫描对热点缓存的污染**。

## 2. 双写缓冲区与页断裂问题（面试高频）

> 🎯【面试题】什么是页断裂（Partial Page Write）？为什么 redo log 解决不了？双写缓冲区是怎么工作的？
> 参考答案：
> - **页断裂的成因**：InnoDB 页 16KB，而磁盘扇区 512 字节、文件系统块通常 4KB，写一个 16KB 的页要拆成 4~32 次物理写入。**写到一半断电**，该页就变成"前半新数据 + 后半旧数据"的坏页，Checksum 校验失败——既不是新数据也不是旧数据，直接损坏；
> - **为什么 redo log 救不了**：redo 记录的是"在某页某偏移上改了什么"，前提是**页本身完好**。页已经断裂，内部结构（指针、记录长度）全乱了，在坏页上重放 redo 只会越改越乱；
> - **双写缓冲区（Double Write Buffer）工作流程**：脏页刷盘时，先把脏页**复制到内存中的 doublewrite buffer** → **顺序写**到系统表空间的双写区域（每次约 1MB）→ 确认写完后，再**随机写**到真正的 `.ibd` 数据文件。崩溃恢复时发现某页 Checksum 损坏，就从双写区域取**完整副本**还原该页，再应用 redo log；
> - **性能代价**：写两次，但第一次是顺序写，整体损耗约 10%，用小代价换数据安全，参数 `innodb_doublewrite` 默认开启。

> ⚠️注意：只有当文件系统/硬件支持**原子写**（如 ZFS、部分企业级 SSD，保证 16KB 一次性落盘）时才可关闭双写换性能；从库若追求极致性能且能接受损坏后重建，也可关闭。
> 一句话：**双写缓冲 = "先备份完整页再落盘"，专门兜底 16KB 页写到一半断电的页断裂问题——redo log 只能救完好的页，救不了碎掉的页**。

# 十二、主从复制（binlog 三种格式）
> 🎯【面试题】MySQL主从复制原理？binlog三种格式的区别？
> 参考答案：主从复制核心是**主库binlog → 从库relay log（中继日志）→ 从库重放**三个步骤：
> 1. 主库的变更写入 binlog；
> 2. 从库IO线程连接主库，拉取binlog写入从库的 relay log；
> 3. 从库SQL线程读取relay log并重放，完成数据同步。
> 复制模式有异步复制（默认，主库不等从库确认）、半同步复制（至少一个从库确认才提交，保证不丢数据）、组复制（MGR）。

**binlog 三种格式：**
| 格式 | 记录内容 | 优点 | 缺点 |
|---|---|---|---|
| STATEMENT | 记录原始SQL语句 | 日志量小 | 依赖上下文，now()/limit等函数重放结果可能不一致 |
| ROW（MySQL8默认） | 记录每行数据变更前后的值 | 最准确，无函数一致性问题 | 日志量大 |
| MIXED | 自动选择：安全场景用statement，否则用row | 兼顾两者 | 逻辑复杂 |

> 🎯【面试题】主从延迟怎么产生？如何解决？
> 参考答案：原因：1. 从库SQL线程单线程重放，主库写入并发高时跟不上；2. 主库大事务（一次性改百万行）重放耗时；3. 从库硬件弱、DDL阻塞。解决：1. 使用**并行复制**（多线程重放，按库/按事务组并行）；2. 拆分大事务；3. 读写分离场景对延迟敏感的业务强制走主库（如刚下单后的订单查询）；4. 提升从库硬件、使用SSD。

# 十三、分库分表（核心思想与问题）
> 🎯【面试题】什么时候需要分库分表？怎么分？带来什么问题？
> 参考答案：单库单表出现瓶颈时考虑——单表数据量过亿、索引层级加深性能下降；单库连接数/IO/CPU成为瓶颈；单机存储容量不足。两种拆分方式：
> - **垂直拆分**：按业务拆库（用户库、订单库、商品库），或按字段拆表（大字段拆副表），本质是"按功能/热度切分"，解决单库压力；
> - **水平拆分**：同一张表按**分片键**（如user_id、order_id取模或按范围）拆到多张表/多个库，每张表数据量均衡，解决单表数据量过大问题。分片键必须选择高频查询字段，否则查询要全分片扫描。

**带来的问题（面试必问）：**
1. 跨库/跨分片 join 失效——需要冗余字段或应用层组装，或反范式冗余数据；
2. 分布式事务——需要可靠消息最终一致性、TCC、Seata等方案；
3. 全局唯一ID——不能用自增主键，改用雪花算法、号段模式（美团Leaf）、UUID；
4. 扩容困难——取模分片后加节点需要数据迁移（一致性哈希或范围分片可缓解）；
5. 排序分页、聚合统计变复杂——需要多分片结果合并。
> 结论：分库分表是**最后手段**，优先通过索引优化、缓存（Redis）、读写分离、归档冷数据解决；中间件常用 ShardingSphere、MyCat。

# 十四、常用字段类型与主键设计（面试高频）
**char 与 varchar：**
- char(n)：定长，长度固定，存不满补空格，存取快，适合长度稳定的字段（手机号、MD5、状态码）；
- varchar(n)：变长，额外1~2字节存长度，节省空间，适合长度可变的字段（用户名、备注）；
- 注意：varchar(255) 以内可以做完整索引，超大varchar（utf8mb4下超过3072字节）无法直接建索引；text/blob不能直接建索引，只能建前缀索引。

**datetime 与 timestamp：**
- datetime：8字节，范围大（1000~9999年），不依赖时区，存什么显示什么；
- timestamp：4字节，范围小（1970~2038年），自动转为UTC存储，跟随会话时区显示，有2038年问题；
- 业务推荐datetime，**create_time/update_time 统一用 datetime，并设置`DEFAULT CURRENT_TIMESTAMP`和`ON UPDATE CURRENT_TIMESTAMP`自动维护**。

**数值类型：**
- 整数：tinyint(1字节)/smallint(2)/int(4)/bigint(8)，**主键用bigint，状态位用tinyint**；
- 小数：金额一律 `decimal(m,d)`（如decimal(10,2)），**禁止float/double存金额**；
- int(11)中的11只是显示宽度，不影响取值范围，MySQL8已废弃该显示宽度。

**主键选择：**
> 🎯【面试题】自增主键和UUID主键怎么选？
> 参考答案：自增主键：占用空间小、插入顺序写性能最高、B+Tree不频繁分裂；缺点是有序可被猜测、分布式多库会冲突。UUID：全局唯一适合分布式，但36字符占用大、无序导致B+Tree随机插入频繁页分裂、性能差。**推荐：单机用自增bigint；分布式用雪花算法（Snowflake，64位长整型，时间戳+机器号+序列号）或号段模式**，兼顾全局唯一与趋势递增。
